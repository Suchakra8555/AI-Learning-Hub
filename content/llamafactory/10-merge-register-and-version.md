An adapter is not something you can hand to most servers. vLLM, KServe and llama.cpp each want one normal model folder. **Merging** adds the adapter's weights into the base model and saves the result.

## The merge

The official config, `examples/merge_lora/qwen3_lora_sft.yaml`:

```yaml
### Note: DO NOT use quantized model or quantization_bit when merging lora adapters

model_name_or_path: Qwen/Qwen3-4B-Instruct-2507
adapter_name_or_path: saves/qwen3-4b/lora/sft
template: qwen3_nothink
trust_remote_code: true

export_dir: saves/qwen3_sft_merged
export_size: 5
export_device: cpu  # choices: [cpu, auto]
export_legacy_format: false
```

- `export_size: 5` splits the weights into files of at most 5 GB.
- `export_device: cpu` merges in system memory, so a GPU is not needed.
- `export_legacy_format: false` saves `.safetensors`, not pickled `.bin` files. Loading safetensors cannot run code.
- With the default `infer_dtype: auto`, a 32-bit model is saved in bfloat16 when the machine supports it, halving the size.

We ran it on the tiny model from the [catalog](lesson:llamafactory/the-example-catalog), with its test adapter. It passed in 44 seconds and wrote:

```text
chat_template.jinja  config.json  generation_config.json  model.safetensors
Modelfile  tokenizer.json  tokenizer_config.json
```

Two things in that folder are easy to miss. The tokenizer is saved too, so the folder is complete on its own. And every export writes an Ollama **Modelfile**, generated from the template:

```text
# ollama modelfile auto-generated by llamafactory

FROM .

TEMPLATE """<|begin_of_text|>{{ if .System }}<|start_header_id|>system<|end_header_id|> ...
```

So a merged folder is already halfway to running in Ollama, with the same prompt format it was trained on.

## Register it

`code/llamafactory/register.py` takes the newest run tagged `gate=pass` (or a run id you pass) and does four things:

```python
# 1. merge, with the official YAML and our paths on top
subprocess.run([CLI, "export", str(MERGE_YAML), f"model_name_or_path=...", f"template=...",
                f"adapter_name_or_path={mlflow.artifacts.download_artifacts(run_id=..., artifact_path='adapter')}",
                f"export_dir={merged}"], check=True)

# 2. log the merged folder into the run that trained it, and register a new version
with mlflow.start_run(run_id=run.info.run_id):
    info = mlflow.transformers.log_model(transformers_model=str(merged), task="text-generation",
                                         name="merged", registered_model_name="nori")

# 3. copy the lineage onto the version
for key in ["base_model", "base_model_revision", "data_digest", "git_commit", "version.llamafactory"]:
    client.set_model_version_tag("nori", v, key, run.data.tags[key])

# 4. point `staging` at it
client.set_registered_model_alias("nori", "staging", v)
```

Step 2 uses something we read in MLflow 3.18's source: `mlflow.transformers.log_model` accepts a folder path as a string. It then requires `task`, and it copies the whole folder, tokenizer included, into the logged model's `model/` folder. So what you download later is the same Hugging Face folder that LLaMA-Factory, vLLM, KServe and llama.cpp all read. Nothing gets re-saved through a pipeline object.

Step 3 matters when you find the version months later in the registry. The version carries its own answer to "what made you", without anyone having to find the run.

## Promote and roll back

```bash
python register.py            # new version, alias staging
python register.py promote    # champion -> whatever staging points at
```

The pipeline may move `staging`. Only a person runs `promote`. Rollback is the [MLflow registry](lesson:mlflow/registry-and-aliases) move: point `champion` back at the previous version. Serving code loads `models:/nori@champion` and never changes.

## What versions what, so far

| Thing | Versioned by | Lives in |
|---|---|---|
| Adapter | the training run | run artifacts, `adapter/` |
| Merged model | registered version `nori/N` | the run's logged model `merged` |
| Its lineage | tags copied from the run | the model version |
| What is live | alias `champion` | the registry |

:::note Not run
The merge ran on the tiny model only. `register.py` was not run: it needs a run that passed the [gate](lesson:llamafactory/evaluate-before-you-ship). The `log_model` behaviour comes from MLflow 3.18.0's source (`mlflow/transformers/__init__.py` and `model_io.py`), not from a test.
:::

:::check Why must you merge into the full-precision base model, not the 4-bit one you trained QLoRA on?
LLaMA-Factory refuses to merge into a quantized model ("Cannot merge adapters to a quantized model"). Merge into full precision, then quantize the merged model if you need it smaller.
:::

:::check A teammate asks which data made `nori` version 3. Where do you look, without opening any training run?
The version's own tags: `data_digest`, plus `base_model_revision` and `git_commit`. `register.py` copies them from the run onto the version.
:::
